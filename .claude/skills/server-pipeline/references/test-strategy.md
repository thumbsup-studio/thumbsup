# Spring 백엔드 테스트 전략 (ATDD + TDD + Outside-In)

> **결론**
>
> Spring Boot 기반 백엔드에서는 다음 조합이 가장 현실적이고 유지보수성이
> 높은 테스트 전략이다.
>
> -   **ATDD(통합 테스트)**로 기능 요구사항과 회귀를 검증한다.
> -   **고전파(Classical) TDD**로 도메인 규칙과 비즈니스 로직을
>     검증한다.
> -   **Mock은 외부 시스템 경계에서만 제한적으로 사용**한다.

------------------------------------------------------------------------

# 왜 이런 전략을 선택하는가?

## 테스트 철학

### Classical TDD (켄트 벡)

-   실제 객체를 사용한다.
-   결과(State)를 검증한다.
-   리팩터링에 강하다.
-   구현 변경에 테스트가 잘 깨지지 않는다.

### London School TDD

-   Mock 중심으로 테스트한다.
-   객체 간 협력을 먼저 설계한다.
-   Interaction(호출 여부)을 검증한다.
-   구현 변경 시 테스트가 자주 깨질 수 있다.

Spring Boot에서는 Testcontainers, 실제 객체 생성 비용, 유지보수성을
고려하여 순수한 한 가지 방식보다 다음과 같은 절충안을 많이 사용한다.

``` text
ATDD (통합 테스트)

↓

Service는 Classical TDD

↓

Repository는 실제 DB(Testcontainers)

↓

외부 API만 Mock
```

즉,

-   요구사항은 **Outside-In**으로 설계하고,
-   내부 구현은 **고전파 TDD**로 검증하며,
-   외부 시스템만 Mock으로 대체한다.

------------------------------------------------------------------------

# 전체 개발 흐름

``` text
1. 요구사항 정의

↓

2. ATDD(통합 테스트) 작성
   ↓
   Red

↓

3. 구현을 위한 단위 테스트(TDD) 작성
   Red → Green → Refactor 반복

↓

4. 기능 구현 완료

↓

5. ATDD 실행
   Green 확인

↓

6. 리팩터링

↓

7. 모든 테스트 Green 확인
```

ATDD는 기능 수준의 안전망이고, TDD는 구현 수준의 안전망이다.

------------------------------------------------------------------------

# 테스트 역할

## 1. ATDD (통합 테스트)

질문:

> **이 기능이 요구사항을 만족하는가?**

검증 대상

-   API 응답
-   HTTP Status
-   DB 상태
-   도메인 결과
-   핵심 비즈니스 시나리오

예시

``` text
POST /signup

↓

201 Created

↓

회원이 저장됨

↓

회원 상태 = ACTIVE
```

ATDD는 기능 단위의 회귀를 막는 것이 목적이다.

------------------------------------------------------------------------

## 2. TDD (단위 테스트)

질문:

> **이 요구사항을 만족시키기 위한 내부 규칙이 정확한가?**

검증 대상

-   도메인 규칙
-   계산 로직
-   정책
-   상태 변화
-   Validation

예시

-   비밀번호 길이 검증
-   숫자 포함 여부
-   특수문자 포함 여부
-   이메일 형식 검증
-   회원 생성 규칙

------------------------------------------------------------------------

## 3. Mock 테스트

Mock은 **외부 시스템과의 경계(Boundary)** 에서만 사용한다.

대표 대상

-   결제 API
-   메일
-   SMS
-   Kafka
-   RabbitMQ
-   Redis Pub/Sub
-   S3
-   Slack
-   외부 REST API

예시

``` text
회원가입 성공

↓

EmailSender.send()

호출 여부 검증
```

# 어떤 테스트를 어디까지 작성해야 할까?

## ATDD

기능의 핵심 시나리오만 검증한다.

예)

-   정상 가입
-   중복 이메일
-   권한 없음
-   주문 성공
-   주문 취소

## 단위 테스트

세부 비즈니스 규칙을 촘촘하게 검증한다.

예)

-   비밀번호 정책
-   이메일 형식 검증
-   할인 계산
-   쿠폰 정책
-   회원 생성 규칙

# 회원가입 예시

## ATDD

``` gherkin
Feature: 회원 가입

Scenario: 정상적으로 회원 가입한다.
  Given 가입되지 않은 이메일이다.
  When 회원 가입을 요청한다.
  Then 201 Created를 반환한다.
  And 회원이 저장된다.
  And 회원 상태는 ACTIVE이다.

Scenario: 이미 가입된 이메일이다.
  Given 이미 가입된 이메일이다.
  When 회원 가입을 요청한다.
  Then 409 Conflict를 반환한다.

Scenario: 비밀번호 정책을 만족하지 않는다.
  Given 가입되지 않은 이메일이다.
  When 정책을 만족하지 않는 비밀번호로 가입을 요청한다.
  Then 400 Bad Request를 반환한다.

Scenario: 이메일 형식이 올바르지 않다.
  Given 올바르지 않은 이메일이다.
  When 회원 가입을 요청한다.
  Then 400 Bad Request를 반환한다.

Scenario: 탈퇴한 회원이 재가입한다.
  Given 탈퇴 이력이 있는 회원이다.
  When 회원 가입을 요청한다.
  Then 정책에 맞는 결과를 반환한다.
```

## TDD

-   PasswordPolicyTest
    -   8자 미만 실패
    -   숫자 미포함 실패
    -   특수문자 미포함 실패
-   EmailValidatorTest
-   UserFactoryTest
-   DuplicateEmailPolicyTest

## Mock

``` text
회원가입 성공

↓

EmailSender.send()

호출 확인
```

# 장점

-   요구사항 중심으로 개발된다.
-   핵심 기능의 회귀를 방지한다.
-   리팩터링이 쉬워진다.
-   테스트가 구현에 과도하게 의존하지 않는다.
-   AI Agent 기반 개발과도 잘 어울린다.

------------------------------------------------------------------------

# 주의할 점

-   통합 테스트를 모든 분기에 대해 작성하지 않는다.
-   단위 테스트를 생략하지 않는다.
-   Mock을 내부 객체까지 남용하지 않는다.
-   Mock은 외부 시스템 경계에서만 사용한다.

------------------------------------------------------------------------

# 최종 테스트 전략

  -----------------------------------------------------------------------
  계층         목적         검증 대상              권장 방식
  ------------ ------------ ---------------------- ----------------------
  ATDD / 통합  기능         API 응답, DB 상태,     실제 애플리케이션 +
  테스트       요구사항     핵심 시나리오          실제
               검증 및 회귀                        DB(Testcontainers)
               방지                                

  TDD / 단위   도메인 규칙  계산, 정책, 상태 변화  고전파(Classical TDD)
  테스트       및 비즈니스                         
               로직 검증                           

  Mock 테스트  외부 시스템  메일, 결제, Kafka, S3  런던파 스타일을
               연동 검증    등                     경계에서만 사용
  -----------------------------------------------------------------------

# 한 줄 요약

> **Outside-In으로 요구사항을 정의하고(ATDD), 내부 구현은 고전파 TDD로
> 견고하게 만들며, Mock은 외부 시스템 경계에서만 사용하는 것이 Spring
> Boot 백엔드에서 가장 실용적인 테스트 전략이다.**
