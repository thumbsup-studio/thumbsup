# 중·상 난이도 오답 시 재도전 1회 — 설계

- **날짜**: 2026-07-19
- **이슈**: [#63](https://github.com/thumbsup-studio/thumbsup/issues/63) (M2)
- **관련 코드**: `app/src/features/play/components/play-page.tsx`, `server/src/main/java/studio/thumbsup/server/quiz/QuizService.java`
- **상태**: 사용자 승인 완료 (2026-07-19) — 구현 대기

---

## 1. 배경 & 문제

지금은 문제를 틀리면 곧바로 해설 화면으로 넘어간다. 오답 후 선형 진행 정책(#19)이다.

팀 회의(2026-07-18)에서 "**힌트 기능 등을 추가해서 유저의 심리적 불편(오답 상황)을 줄여야 한다**"는 문제 제기가 나왔다. 중·상 난이도는 한 번에 맞히기 어려운데, 틀리자마자 정답이 공개되면 학습 기회가 사라지고 좌절감만 남는다.

중·상 난이도에 한해 **재도전 1회 + 부분 힌트**를 제공해 이 두 가지를 동시에 해결한다.

## 2. 목표 / 비목표

**목표**
- 중·상 난이도 오답 시 즉시 해설로 넘기지 않고 재도전 1회 제공.
- 재도전 시 정답을 흘리지 않는 **부분 힌트** 제공(사지선다는 오답 소거, 빈칸은 첫 글자·글자수).
- 하 난이도(OX)는 기존 선형 진행 유지.
- 재도전 최종 결과가 채점·해설·연속 정답에 올바르게 반영.

**비목표 (이번 범위 밖)**
- 사용자가 원할 때 호출하는 힌트 + 무료 횟수/광고/포인트 과금 — 전용 이슈 [#184](https://github.com/thumbsup-studio/thumbsup/issues/184).
- 포인트 차등 지급 — 포인트 경제 자체가 미구현(§3 F4). [#24](https://github.com/thumbsup-studio/thumbsup/issues/24)(M4)의 몫.
- 재도전 횟수 2회 이상, 난이도별 차등 횟수.
- 건너뛰기(#64)·북마크(#36)와의 상호작용 — 두 기능 모두 미구현.
- 화면 회전 정책 — 기존 정책을 그대로 따르며 별도 처리 없음.

### D2를 그렇게 정한 이유 — 기존 필드가 전부 정답을 흘린다

시드 데이터의 실제 사지선다 문제 하나를 보면:

- 정답 선택지: `응용 프로그램이 운영체제 커널의 기능을 요청하기 위한 인터페이스이다.`
- 같은 문제의 키워드 `시스템 콜` 설명: `응용 프로그램이 운영체제 커널의 기능을 요청하는 인터페이스이다.`

**사실상 같은 문장**이라 키워드 설명을 힌트로 띄우면 정답을 그대로 보여주게 된다. 해설 3종(`explanation_summary`, `explanation_example`, `wrong_answer_explanation`)도 모두 `[[시스템 콜]]` 마커로 정답 용어를 명시한다. AI로 힌트 필드를 새로 생성하는 선택지는 마이그레이션+프롬프트 수정+38문제 백필이 필요해 M2(빠른 보완) 범위를 벗어나고, 힌트 전용 이슈 #184와 중복된다.

## 5. 서버 설계

### 5.1 DTO

```java
// server/src/main/java/studio/thumbsup/server/quiz/dto/RetryHint.java
/** 재도전 힌트 — 오답이고 중·상 난이도일 때만 채워진다. 유형에 따라 채워지는 필드가 다르다. */
public record RetryHint(Long eliminatedChoiceId, List<BlankHint> blankHints) {
    /** 빈칸 하나에 대한 힌트. answerLength는 공백을 제외한 글자 수. */
    public record BlankHint(int slotOrder, String revealedPrefix, int answerLength) {}
}
```

```java
// AnswerSubmitResponse — retryHint 필드 추가 (기존 isCorrect 유지)
public record AnswerSubmitResponse(boolean isCorrect, RetryHint retryHint) {}
```

기존 필드를 건드리지 않고 nullable 필드 하나만 추가하므로 현재 앱은 그대로 동작한다.

응답 예시:

```json
{ "isCorrect": false, "retryHint": { "eliminatedChoiceId": 13, "blankHints": null } }
{ "isCorrect": false, "retryHint": { "eliminatedChoiceId": null,
    "blankHints": [ { "slotOrder": 1, "revealedPrefix": "시", "answerLength": 4 } ] } }
{ "isCorrect": true, "retryHint": null }
```

### 5.2 힌트 생성 규칙 (`QuizService`)

다음 중 하나라도 해당하면 `null`을 반환한다.

- 정답인 경우
- 난이도가 `EASY`인 경우
- 유형이 `OX`인 경우 — 힌트로 줄 형태가 없다. 현재 데이터에서 OX는 항상 `EASY`지만(F6) 코드가 그 결합을 가정하지 않도록 유형으로도 막는다

그 외에는 유형별로:

**사지선다 — 소거할 오답 1개**

사용자가 방금 고른 오답을 지우는 건 이미 아는 사실이라 힌트가 되지 않는다. 따라서 **오답 중 사용자가 고르지 않은 것**을 고른다. 4지선다면 오답 3개 중 2개가 후보이므로 항상 하나는 나온다. 표시 순서(`displayOrder`) 기준 첫 번째를 고른다 — 결정적이라 테스트하기 쉽다.

제출값이 숫자로 파싱되지 않으면(기존 `parseChoiceId`가 `null` 반환) 제외 조건 없이 오답 중 첫 번째를 고른다.

**빈칸 — 슬롯별 첫 글자 + 글자수**

슬롯마다 등록된 첫 키워드를 기준으로 첫 글자와 **공백 제외** 글자 수를 준다. "첫 키워드"는 그 슬롯에 등록된 순서(엔티티 id 오름차순) 기준 첫 번째다 — 시드에서 한글 표기가 먼저, 영문 동의어가 뒤에 오므로(`'시스템 콜'` → `'system call'`) 자연스럽게 한글이 힌트가 된다. 목록은 `slotOrder` 오름차순으로 정렬해 내려준다.

빈칸이 2개인 문제가 2건 있으므로 목록으로 내려 슬롯별로 모두 보여준다.

```
'시스템 콜' → revealedPrefix "시", answerLength 4
'데드락'    → revealedPrefix "데", answerLength 3
```

공백을 제외하는 이유는 정답 매칭이 이미 띄어쓰기를 무시하기 때문이다(#183, 머지 완료). `시스템 콜`과 `시스템콜`이 같은 답이므로 글자수도 공백 없는 기준이어야 일관된다.

키워드가 등록되지 않은 문제는 힌트 없이(`null`) 넘어간다 — 시드에 형식이 다른 문제가 1건 있다.

### 5.3 서버 범위 밖

재도전 허용 여부를 서버가 판정하지 않는다. 제출 횟수를 세지 않고 두 번째 제출을 특별 취급하지도 않는다. F1~F3 때문에 그럴 필요가 없고, D4(새로고침 시 부활)와도 맞는다.

## 6. 앱 설계

### 6.1 상태 전환

```
[첫 시도] ──정답────────────────────────────→ 해설 화면
    │
    ├─오답 & 하 난이도 ──────────────────────→ 해설 화면 (기존 동작)
    │
    └─오답 & 중·상 ─→ [재도전] ──정답────────→ 해설 화면 (정답 취급)
                          └────오답──────────→ 해설 화면 (오답 + "왜 틀렸는지")
```

`play-page.tsx`의 `PlayPage`에 상태 2개를 추가한다.

- `retryHint: RetryHint | null` — 재도전 중이면 채워짐. 이 값의 유무가 곧 "재도전 화면인가"
- `hasUsedRetry: boolean` — 재도전을 이미 썼는지

재도전 대상 판정: `quiz.difficulty !== "EASY"` (즉 `MEDIUM` 또는 `HARD`).

제출 처리 흐름:

```
result = await submitQuizAnswer(...)

if (!result.isCorrect && isRetryEligible && !hasUsedRetry && result.retryHint) {
    setHasUsedRetry(true)
    setRetryHint(result.retryHint)
    setDraft(null)          // 이전 입력 초기화 (TC-63-06)
    return                  // 이동하지 않음, 연속 정답도 건드리지 않음
}

// 최종 결과 — 기존 경로 그대로
nextStreak = updateCorrectStreak(...)
router.push(...)
```

`result.retryHint`가 없으면 재도전에 들어가지 않는다. 서버가 힌트를 못 만든 문제(키워드 미등록 등)에서 빈 재도전 화면이 뜨는 것을 막는다.

### 6.2 연속 정답 처리 (D3)

지금은 제출하는 순간 `updateCorrectStreak`가 호출되어 오답이면 즉시 0으로 밀린다. 첫 오답에서 이걸 호출해버리면 재도전에 성공해도 이미 끊긴 뒤다.

**재도전에 들어갈 때는 호출하지 않고, 최종 결과에서 한 번만 호출한다.** 결과적으로:

- 첫 시도 정답 → `+1` (기존과 동일)
- 첫 오답 → 재도전 정답 → `+1` (연속 유지, D3)
- 첫 오답 → 재도전 오답 → `0`

### 6.3 화면

재도전에 들어가면 문제 위에 힌트 영역이 나타난다.

- **사지선다**: 서버가 지목한 선택지를 취소선 + 흐리게 처리하고 `disabled`. **사용자가 처음 고른 오답은 그대로 고를 수 있게 둔다** — 같은 답을 다시 내면 오답 처리되고 재도전이 소진되는 것이 맞다(TC-63-12).
- **빈칸**: 슬롯별로 `시 ○ ○ ○ (4글자)` 형태로 표기.

접근성(TC-63-27·28): 색만으로 구분하지 않고 "오답이에요, 한 번 더 도전해보세요" 문구를 함께 띄운다. 상태 변화는 화면에 이미 있는 `aria-live` 영역으로 읽어준다.

진행 바(`n/5`)는 손대지 않는다 — F5에 따라 자동으로 유지된다.

### 6.4 복습 모드

복습(재풀이)도 같은 `PlayPage`를 쓴다. 분기하지 않고 **복습에도 동일하게 적용**한다 — 코드가 더 단순하고 UX도 일관된다. 복습은 연속 정답을 URL로 들고 다니며 `updateCorrectStreak`를 호출하지 않으므로, 최종 결과의 `isCorrect`만 정확히 전달되면 된다.

- 사지선다 오답 → 소거 선택지가 오답이고, 사용자가 고른 것과 다르다
- 사지선다에서 파싱 불가한 선택지 id 제출 → 오답 중 첫 번째를 소거
- 빈칸 오답 → 슬롯별 첫 글자·공백 제외 글자수. 슬롯 2개면 힌트도 2개
- 정답이면 `retryHint`가 `null`
- 하 난이도(OX) 오답이면 `retryHint`가 `null`
- 정답 키워드가 없는 빈칸 → `retryHint`가 `null`

**앱** (`play-page.test.tsx` 확장)

- 중 난이도 오답 → 해설로 이동하지 않고 재도전 화면 진입, 이전 선택 초기화
- 하 난이도 오답 → 곧바로 해설로 이동(기존 동작 유지)
- 재도전 정답 → 연속 정답 +1로 해설 이동 (D3)
- 재도전도 오답 → 연속 정답 0으로 해설 이동
- 소거된 선택지가 `disabled`이고, 첫 시도에 고른 오답은 여전히 선택 가능
- 재도전 제출 실패 → 에러 UI가 뜨고 재도전 화면이 유지됨
- `retryHint`가 없는 오답 응답 → 재도전 없이 해설로 이동
