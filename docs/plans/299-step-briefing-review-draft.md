# #299 라이브 스텝 브리핑 검수 초안

아래 문안은 각 스텝의 기존 퀴즈 1~5번과 해설을 바탕으로 다시 작성한 초안이다. 정답·선택지·판단 결과를 직접 드러내지 않으며, 승인 전에는 Flyway에 반영하지 않는다.

## 운영체제

### 1. OS 개요와 역할

요약: 운영체제는 프로그램이 CPU·메모리·장치를 안전하게 함께 쓰도록, 프로그램과 하드웨어 사이를 관리하는 소프트웨어다.

1. `CONCEPT` · 두 개의 실행 영역 — 일반 프로그램은 제한된 권한의 사용자 모드에서 실행된다. 반면 커널은 운영체제의 핵심으로, 자원 관리처럼 영향이 큰 일을 더 높은 권한의 커널 모드에서 처리한다.
2. `CONCEPT` · 운영체제에 요청하는 문 — 파일을 읽거나 새 프로세스를 만드는 일처럼 보호가 필요한 기능은 프로그램이 직접 처리하지 않는다. 프로그램은 시스템 콜이라는 정해진 창구로 커널에 일을 요청한다.
3. `EXAMPLE` · 운영체제가 개입하는 순간 — 키보드 입력이나 디스크 작업 완료처럼 장치에서 사건이 생기면 인터럽트가 CPU에 알려 준다. 운영체제는 잠시 제어를 받아 필요한 처리를 한 뒤, 원래 하던 일을 이어 갈 수 있게 한다.

### 2. 프로세스 기본 개념

요약: 프로세스는 실행 중인 프로그램이다. 운영체제는 각 프로세스가 어디까지 실행됐고 무엇을 기다리는지 기록해, 여러 작업을 번갈아 실행한다.

1. `CONCEPT` · 파일과 실행의 차이 — 디스크에 있는 프로그램 파일은 아직 실행 중이 아니다. 이를 메모리에 올려 실행하면 프로세스가 되며, 각 프로세스는 자신의 실행 위치와 할당받은 자원을 가진다.
2. `CONCEPT` · 상태로 보는 실행 흐름 — CPU를 받을 차례를 기다리는 Ready, 실제로 CPU를 쓰는 Running, 입출력 같은 사건을 기다리는 Waiting은 서로 다른 상태다. 사건이 끝나거나 CPU 사용 시간이 지나면 프로세스는 상태를 옮긴다.
3. `CONCEPT` · 멈춘 곳에서 다시 이어가기 — 운영체제는 PCB에 프로세스의 상태, 다음에 실행할 위치, 레지스터 값 등을 보관한다. CPU를 다른 프로세스에 넘길 때 이 정보를 저장하고 다음 정보를 복원하는 일을 문맥 전환이라고 한다.

### 3. 스레드와 멀티스레딩

요약: 스레드는 프로세스 안에서 실제로 명령을 실행하는 흐름이다. 여러 스레드는 자원을 공유해 함께 일할 수 있지만, 그만큼 실행 순서를 조심해야 한다.

1. `CONCEPT` · 무엇을 공유하고 무엇을 따로 가질까 — 프로세스는 주소 공간과 자원의 경계이고, 스레드는 그 안의 실행 흐름이다. 같은 프로세스의 스레드는 코드·데이터·힙을 공유하지만, 각자의 레지스터와 스택은 따로 가진다.
2. `EXAMPLE` · 한 앱 안의 여러 작업 — 브라우저가 화면을 그리면서 네트워크 응답을 기다리는 것처럼, 하나의 프로세스 안에 여러 실행 흐름을 두면 작업을 나눌 수 있다. 스레드를 바꾸는 일은 보통 서로 다른 프로세스 사이를 바꾸는 일보다 공유할 정보가 많아 가볍다.
3. `CAUTION` · 멀티스레딩이 항상 빠르지는 않다 — 실행 대상을 바꾸는 비용, 잠금을 두고 기다리는 경합, CPU 코어 수의 한계 때문에 작업 성격에 따라 오히려 느려질 수 있다. 동시성과 성능 향상은 같은 말이 아니다.
4. `CAUTION` · 공유 데이터를 바꿀 때 생기는 문제 — 증가 연산처럼 짧아 보이는 작업도 읽기·계산·쓰기 여러 단계로 나뉠 수 있다. 여러 스레드가 동시에 바꾸면 결과가 달라질 수 있고, 서로가 가진 잠금을 기다리면 모두 진행하지 못하는 상태가 생길 수 있다.

### 4. CPU 스케줄링 기초

요약: CPU를 기다리는 작업 중 누구를 먼저 실행할지 정하는 기준과, 그 기준이 대기 시간·응답성에 미치는 영향을 살펴본다.

1. `CONCEPT` · 기준이 다르면 실행 순서도 달라진다 — FCFS는 준비 큐에 도착한 순서를, SJF는 예상 CPU 사용 시간이 짧은 작업을, 우선순위 스케줄링은 부여된 중요도를 기준으로 다음 작업을 고른다. 어떤 기준을 쓰는지 먼저 확인해야 실행 순서를 판단할 수 있다.
2. `CONCEPT` · 라운드로빈은 시간을 나누어 CPU를 돌려 쓴다 — 라운드로빈은 각 작업에 타임 퀀텀이라는 시간 조각을 주고 차례로 실행한다. 시간 조각이 작으면 여러 작업이 빠르게 반응할 기회가 늘고, 크면 한 작업이 오래 실행된다.
3. `CAUTION` · 좋은 평균 대기 시간과 실제 적용 가능성은 다르다 — SJF는 짧은 작업을 먼저 처리해 평균 대기 시간을 줄이는 데 유리하지만, 미래의 CPU 사용 시간을 정확히 알기 어렵다. 긴 작업이 계속 뒤로 밀리지 않게 하는 정책도 함께 고려해야 한다.
4. `EXAMPLE` · 시간 조각의 크기는 전환 비용과 응답성 사이의 선택이다 — 대화형 프로그램에서 시간 조각을 매우 작게 하면 여러 프로그램이 곧 반응하는 듯 보일 수 있다. 다만 실행 대상을 자주 바꾸면 문맥 전환 비용이 늘어 실제 작업에 쓸 CPU 시간이 줄 수 있다.

### 5. CPU 스케줄링 심화

요약: CPU를 빼앗을 수 있는지, 작업 성격별로 큐를 나누는지, 오래 기다리는 작업을 어떻게 다룰지를 살펴본다.

1. `CONCEPT` · 선점형과 비선점형은 CPU를 넘기는 시점이 다르다 — 선점형은 운영체제가 실행 중인 작업의 CPU를 회수할 수 있고, 비선점형은 작업이 종료하거나 대기 상태로 들어가는 등의 시점까지 실행을 이어 간다. 이 차이가 응답성과 구현 복잡도에 영향을 준다.
2. `EXAMPLE` · 타이머와 높은 우선순위 작업은 선점의 계기가 된다 — 시간 할당량이 끝나거나 더 중요한 작업이 새로 준비되면, 선점형 정책에서는 실행 대상을 다시 고를 수 있다. 이때 현재 작업의 실행 상태를 저장하고 다른 작업으로 전환한다.
3. `CONCEPT` · 멀티레벨 큐는 작업 성격에 따라 다른 정책을 적용한다 — 대화형 작업과 배치 작업을 서로 다른 큐에 두고, 각 큐에 라운드로빈이나 FCFS처럼 다른 정책을 적용할 수 있다. 일반적인 멀티레벨 큐에서는 한 번 배정된 큐가 고정되며, 실행 중 큐 사이를 이동하는 방식은 멀티레벨 피드백 큐와 구분한다.
4. `CAUTION` · 우선순위 정책은 기아를 만들 수 있다 — 높은 우선순위 작업이 계속 들어오면 낮은 우선순위 작업은 CPU를 매우 오래 기다릴 수 있다. 오래 기다린 작업의 우선순위를 조금씩 높이는 에이징은 이를 완화하는 대표적인 방법이다.

### 6. 프로세스 동기화 기초

요약: 여러 실행 흐름이 같은 데이터를 다룰 때 왜 보호가 필요한지, 뮤텍스와 세마포어가 무엇을 제어하는지 살펴본다.

1. `CONCEPT` · 임계구역과 상호 배제 — 임계구역은 여러 스레드나 프로세스가 공유 데이터에 접근하는 코드 구간이다. 상호 배제는 한 시점에 하나의 실행 흐름만 이 구간에 들어가게 해 실행 순서에 따라 결과가 달라지는 경쟁 상태를 막는 성질이다.
2. `EXAMPLE` · 공유 카운터 갱신은 보호가 필요한 작업이다 — 두 스레드가 같은 카운터의 값을 읽고 각각 증가시킨 뒤 쓰면, 한 증가 결과가 다른 결과를 덮어쓸 수 있다. 잠금으로 증가 구간을 감싸면 한 번에 하나씩 갱신하게 만들 수 있다.
3. `CONCEPT` · 뮤텍스는 한 실행 흐름의 진입을 보호하는 잠금이다 — 뮤텍스는 보통 잠금을 획득한 실행 흐름이 작업을 마친 뒤 해제하는 방식으로 사용한다. 다른 실행 흐름은 잠금이 풀릴 때까지 임계구역에 들어갈 수 없다.
4. `CONCEPT` · 세마포어는 접근 가능한 개수를 센다 — 세마포어는 정수 값과 원자적 연산으로 자원 접근 수를 조절한다. 값이 하나인 경우에는 상호 배제에 쓸 수 있고, 여러 개인 경우에는 같은 종류의 자원을 동시에 몇 개까지 사용할지를 관리할 수 있다.

### 7. 동기화 심화

요약: 생산자와 소비자가 버퍼를 함께 쓸 때 필요한 보호와 대기, 그리고 공유 연산이 원자적이지 않을 때의 문제를 살펴본다.

1. `CONCEPT` · 생산자-소비자 문제에는 두 종류의 제어가 필요하다 — 공유 버퍼의 인덱스·항목 수를 동시에 바꾸지 않도록 상호 배제가 필요하고, 버퍼가 가득 찼거나 비었을 때는 실행을 기다리게 해야 한다. 이 둘은 같은 문제가 아니라 각각 보호와 상태 조율의 역할을 한다.
2. `EXAMPLE` · 버퍼의 빈 칸과 들어 있는 항목 수를 따로 관리한다 — 고정 크기 버퍼에서는 빈 칸 수와 저장된 항목 수를 세는 값으로 생산·소비 가능 여부를 표현할 수 있다. 생산자는 빈 칸이 생길 때까지, 소비자는 항목이 생길 때까지 기다리게 하여 버퍼 범위를 벗어나는 접근을 막는다.
3. `CONCEPT` · 모니터와 조건 변수는 보호와 대기를 구조화한다 — 모니터는 공유 데이터와 연산을 묶어 상호 배제를 제공하는 추상화다. 조건 변수는 원하는 상태가 될 때까지 스레드를 재우고, 상태가 바뀌면 다시 실행 기회를 주는 데 사용한다.
4. `CAUTION` · 한 줄의 증가 연산도 원자적이라고 단정할 수 없다 — 공유 변수의 증가처럼 보이는 연산은 읽기·계산·쓰기의 여러 단계로 나뉠 수 있다. 여러 스레드가 이 사이에 끼어들면 일부 갱신이 사라질 수 있으므로, 락이나 언어가 제공하는 원자 연산이 필요하다.

### 8. 교착상태

요약: 여러 실행 흐름이 자원을 기다리며 멈추는 교착상태의 조건과, 예방·회피·탐지·복구의 차이를 살펴본다.

1. `CONCEPT` · 교착상태는 네 조건이 함께 성립할 때 가능하다 — 상호 배제, 점유와 대기, 비선점, 순환 대기는 교착상태의 필요 조건이다. 네 조건 중 하나라도 성립하지 않게 만들면 교착상태는 발생할 수 없다.
2. `EXAMPLE` · 서로 반대 순서로 잠금을 얻으면 기다림의 고리가 생길 수 있다 — 한 스레드가 A를 잡고 B를 기다리는 동안 다른 스레드가 B를 잡고 A를 기다리면, 둘 다 진행하지 못할 수 있다. 여러 잠금을 사용할 때 획득 순서를 일관되게 정하는 이유다.
3. `CONCEPT` · 예방·회피·탐지·복구는 적용 시점이 다르다 — 예방은 필요 조건을 미리 깨는 설계이고, 회피는 자원을 할당하기 전에 앞으로도 완료 가능한지 검사한다. 탐지는 발생한 교착상태를 찾는 과정이며, 복구는 그 뒤에 문제를 해소하는 단계다.
4. `CAUTION` · 안전 상태와 현재 멈춤 여부를 혼동하지 않는다 — 안전 상태는 어떤 완료 순서를 찾아 모든 프로세스가 끝날 수 있는 자원 할당 상태다. 안전하지 않다는 판단이 즉시 교착상태 발생을 뜻하는 것은 아니지만, 이후 요청을 허용할 때 위험이 될 수 있다.

### 9. 메모리 관리 기초

요약: 메모리를 나누고 배치하는 방식에 따라 단편화, 주소 변환, 보호 방식이 달라진다.

1. `CONCEPT` · 연속 공간이 필요한 배치 — 연속 할당은 프로세스를 한 덩어리의 물리 메모리에 둔다. 빈 공간의 총합이 충분해도 하나로 이어진 공간이 없으면 큰 프로세스를 배치할 수 없다.
2. `CONCEPT` · 고정 크기와 가변 크기 — 페이징은 논리 메모리와 물리 메모리를 같은 크기 단위로 나눠 흩어진 위치에도 배치할 수 있다. 세그멘테이션은 코드·데이터·스택처럼 의미 있는 가변 크기 구역을 다룬다.
3. `CAUTION` · 단편화가 모두 사라지는 것은 아니다 — 페이징은 큰 연속 공간이 필요 없어 외부 단편화를 줄이지만, 마지막 고정 크기 단위의 남는 공간처럼 내부 단편화는 생길 수 있다. 가변 크기 구역은 논리적 보호에 유리하지만 외부 단편화 가능성이 있다.
4. `CONCEPT` · 주소를 실제 위치로 바꾸는 과정 — 페이징에서 CPU가 만든 주소는 페이지 번호와 그 안의 위치로 나뉜다. 페이지 번호를 페이지 테이블에서 프레임 번호로 바꾼 뒤에야 물리 메모리 위치를 찾을 수 있다.

### 10. 가상 메모리

요약: 필요한 페이지를 메모리에 올리고, 공간이 부족하면 일정 기준으로 교체하면서 성능 저하를 관리한다.

1. `CONCEPT` · 접근과 적재는 별개 — 유효한 가상 주소를 접근해도 해당 페이지가 물리 메모리에 없을 수 있다. 이때 운영체제는 보조기억장치에서 페이지를 가져와 프레임에 적재하고 실행을 이어 간다.
2. `CONCEPT` · 교체 기준의 차이 — FIFO는 먼저 메모리에 들어온 페이지를, LRU는 가장 오래 참조되지 않은 페이지를 기준으로 삼는다. 미래 참조를 정확히 안다는 가정의 이론적 기준과, 과거 사용 이력을 쓰는 실제 기준을 구분해 보자.
3. `CAUTION` · 메모리를 더 준다고 항상 폴트가 줄지는 않는다 — 일부 교체 기준에서는 프레임 수를 늘려도 페이지 폴트가 늘어날 수 있다. 페이지 교체 알고리즘은 단순히 ‘더 많은 메모리’만으로 평가되지 않는다.
4. `CAUTION` · 폴트 한 번과 시스템 전체의 악화는 다르다 — 페이지를 자주 교체하느라 실제 실행보다 메모리 관리에 시간을 더 쓰는 상태가 될 수 있다. 이때는 각 프로세스가 자주 쓰는 페이지 집합을 담을 수 있는지와 동시에 실행하는 프로세스 수를 함께 봐야 한다.

### 11. 파일 시스템

요약: 파일은 디스크 블록에 저장되며, 배치 방식과 메타데이터 구조가 접근 성능·확장성·이름 관리를 결정한다.

1. `CONCEPT` · 파일 블록을 배치하는 세 방식 — 연속 할당은 이웃한 블록에 저장해 직접 접근에 유리하지만 확장이 어렵다. 연결 할당은 다음 블록 정보를 따라가며 흩어진 공간을 쓸 수 있고, 인덱스 할당은 블록 주소를 모아 직접 접근을 지원한다.
2. `EXAMPLE` · 연결 정보를 표로 관리하는 방식 — 한 파일의 블록이 물리적으로 흩어져 있어도, 각 블록의 다음 위치를 표에 기록하면 순서대로 파일을 읽을 수 있다. 이는 연결 관계를 별도 테이블에서 관리하는 파일 시스템의 발상이다.
3. `CONCEPT` · 이름과 파일 정보의 역할 분리 — 유닉스 계열에서는 디렉터리 항목이 파일 이름을 파일 정보 구조와 연결하고, 그 구조가 권한·소유자·크기·데이터 블록 위치 같은 메타데이터를 관리한다.
4. `EXAMPLE` · 여러 경로가 하나의 파일을 가리키는 경우 — 링크를 사용하면 서로 다른 디렉터리 경로에서 같은 파일을 참조할 수 있다. 따라서 계층형 디렉터리라고 해서 파일이 반드시 하나의 이름이나 경로만 가져야 하는 것은 아니다.

### 12. 입출력과 디스크 관리

요약: 입출력은 장치와 프로그램의 속도 차이, 장치 공유, 디스크 헤드 이동을 함께 관리해야 한다.

1. `CONCEPT` · 버퍼링과 작업 대기열의 목적 — 버퍼링은 메모리의 중간 저장 공간으로 생산자와 소비자의 속도 차이를 완화한다. 여러 독립 작업을 장치에 쌓아 한 장치를 차례로 공유하게 하는 방식은 별도의 작업 대기열 관리다.
2. `EXAMPLE` · 한 대의 프린터를 여럿이 쓰는 상황 — 여러 프로그램이 인쇄를 요청하면 요청을 대기열에 보관하고 프린터가 순서대로 처리할 수 있다. 프로그램은 즉시 인쇄가 끝날 때까지 장치를 독점할 필요가 없다.
3. `CONCEPT` · 가까운 요청 우선과 공정성 — 디스크 헤드에서 가까운 요청을 먼저 처리하면 평균 이동 거리를 줄일 수 있지만, 먼 요청이 계속 밀릴 수 있다. 헤드가 한 방향으로 이동하며 요청을 처리한 뒤 반대 방향으로 바꾸는 전략은 이런 공정성 문제를 완화하는 데 쓰인다.
4. `CAUTION` · 알고리즘마다 기준이 다르다 — 도착 순서를 따르는 방식, 현재 위치에서 가까운 요청을 고르는 방식, 이동 방향을 유지하는 방식은 서로 다르다. ‘빠른 평균 이동’과 ‘모든 요청의 기다림’은 같은 목표가 아닐 수 있다.

## 디자인 패턴

### 1. 생성 패턴 개요와 싱글턴

요약: 생성 패턴은 객체를 만드는 책임을 분리해, 사용하는 코드가 구체적인 구현과 생성 절차에 덜 묶이게 한다. 싱글턴은 그중 하나의 인스턴스만 두려는 패턴이다.

1. `CONCEPT` · 생성 책임을 감추는 이유 — 생성 패턴은 어떤 구체 클래스를 만들지와 생성 절차를 사용하는 코드 밖으로 분리한다. 구현 교체나 생성 규칙의 변경이 필요할 때 변경 지점을 한곳으로 모을 수 있다.
2. `CONCEPT` · 싱글턴의 두 가지 역할 — 싱글턴은 외부에서 임의로 객체를 만들지 못하게 하고, 정해진 접근 경로로 하나의 인스턴스를 사용하게 한다. 다만 ‘인스턴스가 하나여야 한다’는 요구와 ‘여러 스레드에서도 안전하다’는 요구는 별개다.
3. `EXAMPLE` · 지연 생성이 겹치는 상황 — 아직 객체가 없을 때만 만들도록 구현해도, 두 실행 흐름이 거의 동시에 확인하면 각각 생성을 시도할 수 있다. 생성 여부 확인과 생성 과정을 함께 보호해야 하는 이유다.
4. `CAUTION` · 동시성 최적화에는 언어 규칙까지 필요하다 — 불필요한 잠금 비용을 줄이려고 검사와 동기화를 조합하는 구현은 메모리 가시성과 초기화 규칙을 함께 만족해야 한다. 단일 인스턴스가 편리해도 전역 의존성이 늘면 테스트와 교체가 어려워질 수 있다.

### 2. 팩토리 메서드와 추상 팩토리

요약: 팩토리 계열 패턴은 객체를 직접 만들지 않게 해 생성 지식을 분리한다. 다만 개별 생성 지점을 바꾸는 경우와 함께 쓰이는 여러 객체를 맞춰 만드는 경우는 구분해야 한다.

1. `CONCEPT` · 팩토리 메서드는 생성 결정을 하위 구현에 맡긴다 — 상위 타입은 객체를 만드는 인터페이스를 두고, 어떤 구체 구현을 만들지는 하위 타입이 정하게 한다. 사용 코드는 구체 클래스 이름에 덜 의존하면서 생성 대상을 확장할 수 있다.
2. `CONCEPT` · 추상 팩토리는 관련된 객체 묶음을 함께 만든다 — 버튼·체크박스처럼 함께 사용되는 여러 객체를 같은 계열로 생성하는 인터페이스를 제공한다. 사용하는 코드는 각 객체의 구체 구현을 몰라도 일관된 조합을 받을 수 있다.
3. `EXAMPLE` · 테마를 한 번에 바꾸는 경우 — Windows 테마와 macOS 테마처럼 버튼·체크박스·스크롤바를 같은 모양과 규약으로 맞춰야 한다면, 현재 계열에 맞는 생성 도구를 바꾸는 것만으로 관련 객체들을 함께 교체할 수 있다.
4. `CAUTION` · 확장에 유리한 방향이 다르다 — 팩토리 메서드는 하나의 생성 지점을 상속으로 바꾸는 데 가깝고, 추상 팩토리는 관련 객체의 조합을 바꾸는 데 가깝다. 새 계열을 더하는 일과 기존 계열마다 새 종류의 객체를 추가하는 일의 수정 범위도 다르다.
